# V5: fixing generalisation to the unseen country instead of adding model complexity

## What the leaderboard told us

| system | validation F0.5 (US/India, SIM19) | leaderboard (20 % public) | test matches |
|---|---|---|---|
| V2: XGB stage 1 + stage 2 | 0.98696 | **0.98332** | 5,842,005 |
| V3: + XLM-R + GNN | 0.99078 | 0.982814 | 5,908,644 |
| V4A: V3 chain-A replay, validation-style cosine | 0.99075 | 0.981 | 5,923,052 |
| top team | – | 0.994078 | – |

* **The validation-to-leaderboard gap grows with model complexity**, and the leaderboard gets worse as the system
  accepts more pairs. Validation rewards the GNN/XLM-R, but the test set doesn't.
* **The bi-encoder cosine is not the cause.** On test, the 5-model average and the validation-style single model
  correlate 0.96 over all pairs and 0.985 on each record's top pair (mean |difference| 0.035, `results/phase2/cos/`).
  V4A, which fixed it, scored lower.
* **The likely cause is France.** France is 15 % of test S1, has no training labels, and differs structurally from
  US/India. Its S1 names come from a small generic vocabulary ("Nantes Club SAS", "Association de Formation",
  "Lycée …") in ~20 dense cities of three regions. S2/S3 records use departments instead of regions, upper case,
  `N°/Nº/#` number prefixes, and spurious accents ("Çhasse", "Àmis"). A model that learned "very similar name ⇒ same
  business" on distinctive US/Indian names over-accepts in France, where many different businesses share such
  names and only the address separates them.
  If US/India score about what validation says (~0.987–0.99), France would have to be around 0.94–0.96 to explain
  0.983. That's the single largest recoverable loss (~0.005–0.007 of leaderboard F0.5).
* One normalisation bug showed up: `N°` becomes the junk token `ndeg`, which stays in French addresses.
  It's handled in the V5 street features.

## V5 design (keeps the V2 recipe, the best on the leaderboard)

1. **Transferable features** (`code/v5/extra_feats.py`, 21 new columns). They describe *how much the evidence is
   worth*, not what French names look like:
   * *ambiguity*: how many S1s score within 0.05/0.15 of the best name/address retrieval score for this record, the
     best-vs-second gap, and this S1's score gap to the best;
   * *specificity*: document frequency of the rarest name token of the S1, of the record, and of the rarest *shared*
     token (a shared rare token is strong evidence, a shared generic token is weak);
   * *street core*: address comparison without numbers, street types and noise tokens (`ndeg`, `no`, `bis`).
2. **The same V2 training recipe on the extended table.** Stage 1 is full + no-embedding XGBoost blended
   0.75/0.25 (0.5/0.5 for unseen countries), then an XGBoost stage 2 with context and sibling features,
   isotonic calibration, and expected-F0.5 decoding. There's no GNN or XLM-R, because both lowered the
   leaderboard.
3. **Unseen-country decoding learned from a leave-one-country-out run.** Stage 1 is refit on India only and
   applied to the US as an unseen country. The expected-F0.5 strictness (γ) that works best on the unseen country
   there is applied to France (`best_gamma_unseen`). No test labels are used.
4. **France self-training** (`code/v5/pseudo_label.py`; transductive use of the unlabelled test data, which you
   confirmed is allowed). Records whose best S1 is very confident (calibrated p ≥ 0.97, margin ≥ 0.5) *and*
   whose address independently agrees (same house number, address jaccard ≥ 0.3) become positives, and their
   other candidates negatives. Records with p ≤ 0.02 become distractor negatives. Stage 1 is refit with these
   French rows added, and France is re-scored. US and India keep the V5 scores.
   The identical procedure is first tested on India → US (`loco_eval.py pl`). It's only used if it helps the
   unseen country there by > 0.001 **and** the pseudo-positives were ≥ 99 % correct.
5. **Error accounting** (`code/v5/recall_report.py`): candidate recall, stage-1 recall, top-1 recall, final
   P/R/FP/FN, FN and FP by cause, and how many missed pairs exact name-key or house-number+street blocking would
   recover. This shows whether better blocking is worth building next.

## Decision rule (fixed in `code/v5/choose_v5.py`, written before any V5 result)

1. V5 features are kept only if min(F0.5 fold 0, fold 4) ≥ V2's − 0.0002 **and** they are not worse on the
   unseen country in LOCO (India → US) by more than 0.0005.
2. Pseudo-labels are used only if they raise unseen-country F0.5 in LOCO by > 0.001 with pseudo-positive
   precision ≥ 0.99.
3. Submission order: `final_v5pl` → `final_v5` → keep V2. The rule's output is in `results/v5/v5_choice.json`.

## Run (on the machine with the V2 cache and the data)

```bash
bash run_all.sh --stage v5all          # v5 -> loco5 -> v5pl -> v5final, about 7-8 h on a MIG slice, less on a full H100
cat results/v5/v5_choice.json          # which file to submit first
```

The submission files are `results/final/final_v5pl/output/matching_results.tsv` and
`results/final/final_v5/output/matching_results.tsv`. Both are validated by the runner.

## Honest expectation

V5 targets the part of the gap we can explain: France. If France is at ~0.95 and V5 brings it to ~0.97–0.98, the
leaderboard moves by roughly +0.003–0.005, to about 0.986–0.988. Reaching the top team's 0.994 would need
France *and* US/India near 0.995, and nothing measured so far supports that yet. After this run,
`recall_report.py` and the LOCO numbers show where the next gain is: blocking recall, France, or the pair model.
