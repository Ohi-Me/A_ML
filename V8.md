# V8: more recall, fewer pairs, and the names that link the hardest records

## 0. Targets and where we are

| | now | V8 aims for |
|---|---|---|
| F0.5, leaderboard | V6 0.988109 (leader 0.99765) | as high as the validation allows |
| F0.5, validation (DMS, min of folds 0 / 4) | V6 0.99127 | 0.997 needs both limits below lifted |
| candidate recall (DMS) | 0.988 (C2) | ≥ 0.99, ideally ≥ 0.995 |
| candidate pairs | 83 M on test (8.2 per record); V7 plans up to 12 per record | fewer than C2 |

Two limits stop validation at ~0.991 today:
1. **Candidates.** A perfect scorer on C2 reaches only 0.99635. V7 widens candidate generation, but it also grows the
   table (budget 12 pairs per record), and its string-feature stage needs ≥ 128 GB RAM at that size.
2. **The empty-address records.** 147 k true pairs (2 % of all) have no address and a name key that 82 S1 share on
   average (`results/v6/data_probe.json`, T3). Text similarity to the S1 can't tell which one it is. This block alone
   costs more than the gap between 0.991 and 0.997.

## 1. What V8 changes (on top of V7)

| stage | V7 | V8 |
|---|---|---|
| diagnostics | miss probe, error dump | + `code/v8/sib_probe.py`: do a record's siblings share its **exact normalised name** (typos, legal words), same / other source, and how pure are those name groups? Split by empty-address and ambiguous-key records. + a report-only id check (does the numeric part of ids correlate between S1 and records? No model reads ids). + the miss probe now measures a `sib_name` pass |
| candidate union | lists re-cut on the universe's S1, deeper lists, exact blocks, address/key siblings; budget 12 per record | built **wide** (`cands_plan.py --wide --budget 24`): depth x2/x4 at ≥ 0.0002 recall, block passes up to 3 pairs per record, and the new **`sib_name` pass**: siblings = records with the identical normalised full name in the country (groups ≤ cap), their top-1 candidates are added. It reaches empty-address records, which V7's `sib_key` (key + state) can't group with their addressed siblings |
| **pruner (new)** | – | `code/v8/prune.py`: XGBoost on features that cost almost nothing (list ranks, pass flags, TF-IDF and bi-encoder cosines, their competition over the record's and the S1's candidates, exact-equality flags, key frequencies). Same halves as every model. Cut fixed in advance: keep a pair if its score ≥ τ or it is in the record's top 2, at most 10 per record; τ = the 0.05 % quantile of the true pairs' scores on folds 1-2. The pruned table is the matching model's input and the submitted `candidate_pairs.tsv` |
| memory | ≥ 128 GB for the test pair features | the pruner's features are built in record-aligned chunks; the heavy stage only sees the pruned table |
| collective rounds | address / number / key sibling evidence | + `c_name_same`, `c_name_cross`: the best probability among the S1's confident siblings with the identical normalised name, same / other source |
| stage 1, cross-encoders, rounds, decoding, test chain | V7 | unchanged code, V8 tables (`xgb_v8_*`, `ml_v8*`) |
| choice | V7 vs V6 | `code/v8/choose_v8.py`: V8 first if DMS(V8) ≥ best of V6 / V7 + 0.0005 and the US/India consistency check passes (V6 rule) |

Why the pruner helps accuracy and not only speed: the wide union finds more true pairs, and the pruner removes the
obvious non-matches, so stage 1 and the cross-encoders see fewer, harder competitors per record. The runner-up is
always kept, so the competition features still see it.

## 2. Run (H100, on the V6 cache)

```bash
nohup bash run_all.sh --stage v8all > run_v8.out 2>&1 &
```

| block | what | estimate |
|---|---|---|
| `v8diag` | sibling/name probe + id check; miss probe with `sib_name` | 30–45 min |
| `v8cands` | wide plan, wide train/test candidates, pair cosines | 40–60 min |
| `v8prune` | pruner features (chunked), fit, cut train/test | 45–75 min |
| `v8feat` … `v8pick` | the V7 chain on the pruned candidates | 6–8 h |

Knobs (environment): `V8_BUDGET` (wide union, default 24 pairs per record), `V8_MAX_LOSS` (pruner loss, default
0.0005), `XENC3_MODEL=Qwen/Qwen3-Reranker-0.6B` (third cross-encoder, Apache-2.0, +2–3 h; recommended when time
allows, since the remaining loss is recall inside the candidates).

**Send back right after `v8diag`:** `results/v8/sib_probe.json`, `results/v7/miss_probe.json`,
`results/v7/missed_sample.tsv`. After `v8prune`: `results/v8/prune_c3wdms.json`, `results/v8/prune_apply_*.json`,
`results/v7/cands_c3wdms_train.json`.

## 3. How to read the first numbers

* `sib_probe.json → normalised_name.empty_address_ambiguous_key`: if `has_sibling_same_name_with_address` is high
  (say > 0.5) and `purity_mean` is high (> 0.8), the name-sibling evidence can resolve a large part of the 147 k
  hardest pairs. If both are low, those records are truly ambiguous and 0.997 is out of reach for this block.
* `id_check`: `|spearman_true_pairs|` near 0, like `spearman_random_pairs`, means ids carry no information. If it is
  clearly not 0, **stop and tell the user**: that would be a data leak, and using it is a fair-play question for them
  to decide, not something the pipeline does.
* `prune_c3wdms.json`: `pairs_per_record_after` (target < 8.2) and `by_fold.0.kept_share_of_true` (≥ 0.9995).
* `cands_c3wdms_train.json → recall`: the wide union's recall on DMS (C2: 0.988).

## 4. Honest expectations

The pruner and the wide union should give recall ≥ 0.99 with fewer pairs than C2. Whether validation reaches 0.997
depends on the sibling probe: the empty-address block is the single biggest loss, and no scorer can fix it without a
signal that links those records. V8 measures that signal first and uses it if it's there.
